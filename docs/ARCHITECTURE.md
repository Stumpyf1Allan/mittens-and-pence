# How Mittens & Pence is put together

For whoever maintains this. About 8,000 lines of Python and vanilla JavaScript, with
one required third-party package.

## Shape

```
run_kestrel.py            double-click entry point
kestrel/
  main.py                 CLI, starts the server, opens the window
  config.py               paths, defaults, the sector and category taxonomies
  db.py                   SQLite schema, connections, fingerprints, backups
  security.py             encrypted credential vault
  demo.py                 the sample household (also the test fixture)
  updates.py              find a new version, verify it, stop short of installing it

  institutions/
    registry.py           search, and "what can I do with this bank?"
    data/*.json           275 institutions, generated by tools/build_institutions.py
    websites.py           verified home pages — every URL fetched, none recalled

  providers/              anything that fetches without a file
    base.py               Provider interface + registry
    crypto.py             Kraken, Binance, Coinbase, Luno, VALR — one base class,
                          five signing rituals; balances become holdings
    monzo.py              Monzo's own OAuth client — free, redirect flow
    starling.py           Starling personal access token — free, no redirect
    truelayer.py          UK Open Banking (redirect flow) — needs a paid plan
    enablebanking.py      EEA Open Banking — no UK/ZA, so nothing routes to it
    gocardless.py         ex-Nordigen, for existing keys
    trading212.py         broker API
    investec.py           SA programmable banking
    ibkr.py               Flex Web Service

  importers/              anything that arrives as a file
    readers.py            CSV/Excel/OFX/QIF → header + rows; date and amount parsing
    profiles.py           known statement layouts

    ingest.py             write to the database, de-duplicated

  market/
    prices.py             live quotes, FX, month-end history, offline fallbacks

  engine/

    categorise.py         rules engine + ~200 built-in UK/SA merchant patterns
    budgets.py            budgets, spend rollups, pace, suggestions

  export/

    static/               index.html, app.js, styles.css — no build step
```

## Choices worth knowing about

**The standard library does the serving.** No FastAPI, no uvicorn. For a single-user
local app they'd add ~30 MB to the frozen binary and a pile of PyInstaller hooks for
no benefit. `ThreadingHTTPServer` plus a forty-line regex router is plenty, and the
whole app freezes to 48 MB.

**openpyxl is the only hard dependency.** The price fetcher talks to Yahoo, Stooq and
Frankfurter over `urllib` rather than pulling in `yfinance` and with it pandas and
numpy. `keyring`, `cryptography` and `pywebview` are strongly recommended but each has
a working fallback, and Settings shows which is active.

**No build step for the front end.** Vanilla JS, hand-written CSS, SVG charts drawn in
about eighty lines. It works offline, which a CDN-dependent page would not, and there
is nothing to rebuild when someone edits it in three years' time.

**Everything imported carries a fingerprint.** A SHA-256 of the fields that identify a
row, unique per account. Re-importing an overlapping statement is a no-op. This is the
single most important property of the whole importer, because banks only ever let you
download a rolling window.

**Cost basis is average-cost, replayed from trades.** `rebuild_holdings` walks the
trade history in order; a sell reduces cost proportionally, and a position reaching
zero becomes a Sold row with the dividends it collected while held. A trade's `total`
is always in the *account's* currency, never the price currency — getting that wrong
divides GBX-quoted holdings by a hundred, and there's a test for it.

**The registry is generated, not hand-maintained.** `tools/build_institutions.py`
holds compact tables and expands them into the JSON that ships. Change the tables and
re-run it. `effective_recommendation()` is the single place that decides what Mittens & Pence
suggests, so the badge in the picker and the detail panel can't drift apart.

**Snapshots are honest about what they can't know.** A snapshot taken live records
market values. One reconstructed for a month before Mittens & Pence existed fetches month-end
prices where the feed has them and falls back to cost where it doesn't — and either
way sets `estimated: true` with a note, which the chart renders as hollow points.
Never quietly fabricate history.

**FX has a floor, not a default of 1.0.** If every source fails, `fx_rate` uses a small
table of indicative rates and marks them `fallback`; if the currency isn't in that
table it raises rather than returning 1.0, because silently adding rand to pounds is
worse than an error. `convert()` catches that and records the pair in
`market.UNCONVERTED` for the UI.

## Database

SQLite, WAL mode, foreign keys on, one thread-local connection per worker.
`SCHEMA_VERSION` is in `db.py`; the schema is `CREATE TABLE IF NOT EXISTS` throughout,
so adding a table is safe. Adding a *column* needs a migration — there isn't a
framework for it yet; add one when you first need it.

Tables worth understanding:

* `connections` — one per institution per member. `method` is how data arrives
  (`openbanking` / `direct_api` / `aggregator` / `csv` / `manual`); `status` is
  what the UI badges.
* `transactions` — bank side. `UNIQUE(account_id, fingerprint)`.
* `trades`, `dividends`, `cash_events` — investment side, same fingerprint pattern.
* `holdings` — derived from trades (`source='trades'`), or imported directly
  (`source='import'`), or from an API (`source='api'`), or typed in (`source='manual'`).
  `rebuild_holdings` only ever clears the first two.
* `snapshots` — `UNIQUE(period, scope)`; scope is `household`, `member:<id>`,
  `account:<id>` or `wrapper:<name>`.
* `import_mappings` — keyed on a hash of the header row. This is what makes month two
  a single click.

## Adding things

**A new institution:** add a row to the tables in `tools/build_institutions.py` and
re-run it. The tuple is `(name, kind, group, sync, csv_where, csv_profile, aka)`.

**A new statement format:** add an entry to `PROFILES` in `importers/profiles.py`.
`must` is the columns that have to be present; matching an exact column name scores
higher than matching a fragment, which is what keeps Lloyds and Santander apart. If
the format needs real logic rather than column mapping, set `handler` and write a
`_activity_<name>` function in `ingest.py`.

**Three gates before a route can be recommended.** Each one exists because it was
missed once and produced a bug a beta tester found:

1. *Self-serve* — can an individual sign up at all? (`self_serve` in `providers.json`.)
2. *Built* — is there a client class behind the id? `registry.set_built_providers()` is
   injected by `providers.load_all()`, so the registry can't offer a route with no code.
   Without this, Monzo's setup screen said "supports Open Banking" and showed an Upload
   button in the same breath, because the catalogue named Enable Banking and nothing
   implemented it.
3. *Free* — `provider_is_free()`. TrueLayer passes the first two and still fails here:
   its free console is sandbox only. Without this gate, Mittens & Pence sent someone to a screen
   that warns them not to enter their real bank details.

`effective_recommendation()` applies all three; `ready_providers` is what the UI may
choose from (free first), `paid_providers` is offered as an explicit opt-in, and
`documented_only` is named but greyed out. Two tests hold the line —
`test_an_automatic_recommendation_always_has_a_provider_behind_it` and
`test_an_automatic_recommendation_is_always_free` — plus one asserting every catalogue
entry states `free` explicitly, because a *missing* flag reads as False and silently
demotes an institution to statement upload. That is how Investec lost its own API for
an afternoon. `tools/build_institutions.py` prints both the *supported* and the
*offered* route counts, so a build can't look healthy while every bank quietly points
at a paid sandbox.

`sync.repair_connections()` runs at start-up and re-points any connection saved against
a provider that has since gone, or been demoted — that's how an early beta connection
pointing at Enable Banking heals itself.

**A new provider:** subclass `Provider`, declare `credential_fields` and
`setup_steps`, implement `validate()` and `sync()`, and decorate with `@register`.
Add it to `providers.base.load_all()`. Redirect-flow providers also implement
`begin_link` and `complete_link`; the callback at `/oauth/callback` dispatches on the
`state` parameter.

**A new categorisation rule:** append to `BUILTIN` in `engine/categorise.py`. Built-in
rules are seeded into the `rules` table on first run, so the household can edit or
delete any of them.

## Testing

```
python -m pytest tests -q
```

53 tests. The fixture loads the demo household, which is generated in the *real* file
formats and pushed through the *real* importers — so if the demo loads, the importers
work. The export tests compare the workbook back against the engine cell by cell, and
one test walks every formula in both workbooks rejecting anything LibreOffice can't
evaluate.

Screenshot testing is worth keeping up: Playwright against the local server catches
layout bugs the unit tests can't. Two real bugs came out of it — an invisible `[hidden]`
modal swallowing every click, and a picker list clipped by its scroll container.

## Packaging

`build/mithapp.spec` is a folder build (`dist/Mittens & Pence/Mittens & Pence.exe`), not one-file:
faster to start, and far less likely to upset antivirus. UPX is off for the same
reason. PyInstaller can't cross-compile — build the Windows app on Windows.

The spec bundles `web/static` and `institutions/data` as data files;
`config.resource_dir()` finds them under `sys._MEIPASS` when frozen and beside the
package when not.


## Unknown is not zero

Two columns carry an explicit "we don't know" state, because in both cases the obvious
default was a confident lie:

* `accounts.balance` is **NULL**, not 0. A statement with no running-balance column tells
  Mittens & Pence nothing about the balance, and "£0.00" beside 686 transactions is
  indistinguishable from a genuinely empty account. NULL renders as "—".
* `holdings.cost_known` is **0** when nobody has said what a position cost. A crypto
  exchange reports quantities and never prices, so cost sits at 0 — and a £5,000 holding
  with a £0 cost would otherwise be reported as £5,000 of pure profit. `holdings_rows()`
  returns `money_made = None` in that state, and `rebuild_holdings()` sets `cost_known=1`
  when it replays a real trade history, which is how an uploaded statement repairs a
  connected exchange.

`db.ADDED_COLUMNS` is the migration path for both. `CREATE TABLE IF NOT EXISTS` never
alters a table that already exists, so a new column in `SCHEMA` is invisible to anyone
who already has a database — `_apply_added_columns()` runs on every `init()` and adds
what is missing. Additive columns with defaults only; it is deliberately not a general
migration engine, and it never lets a failure stop the app from opening.


## The logo

`web/static/logo.webp` is a **12 x 10 sprite sheet of 120 frames at 139 x 96**, not an
animated image. It comes from a 10-second 1280x720 video (3.3 MB, with an audio track
nobody wants), and **`tools/make_logo.py` rebuilds it end to end** — strip audio, key the
cream background to alpha, un-multiply, crop, scale, halve to 12 fps, denoise, pack. The
script reproduces the shipped file byte for byte and prints the `styles.css` line that
must match it.

**The frame is not square, and that is the point.** The picture is a cat on a spread-out
pile of money, about 1.44:1. The first sheet forced it into a square, which did two bad
things at once: it cropped flush, so the pile was sliced off at x=0 and read as a
rendering fault, and when the crop was fixed the letterboxing left two fifths of every
frame empty — so the sheet had to be scaled *up* in the sidebar to make the cat a
sensible size, and an upscaled sprite looks soft. A frame shaped like the picture is
sharper and smaller at the same time. `--fw` is derived from `--fh` by that ratio, and a
test checks the CSS against the sheet rather than trusting a number written down twice.

Four decisions worth keeping:

* **Key by connectivity, not colour distance.** The banknotes have pale areas close
  enough to the cream background that a plain threshold punches holes through the middle
  of the pile. The mask is the cream region *reachable from the frame border* — that is
  what background means — then closed and hole-filled.
* **Un-multiply the key colour at soft edges.** A feathered edge still carries cream, and
  cream against `#151d26` reads as a pale halo. Each partly-transparent pixel has the key
  colour divided back out.
* **One crop box for all 120 frames.** Cropping each frame to its own content makes the
  cat swim about inside its own logo as it moves. The box is the union of every frame's
  content plus a 3% margin — so the whole picture is inside every frame, and a test
  fails the build if any frame's alpha touches its own edge.
* **A sprite sheet rather than animated WebP or APNG.** Those loop forever with no way to
  stop them, and restarting one means re-fetching or juggling blob URLs. Stepping a
  sprite from CSS means the animation runs exactly when told and rests on frame 0.
  `--cols` / `--rows` / `--play` in `styles.css` are the only numbers; `sprite-x` steps
  across a row once per second and `sprite-y` steps down a row each time X wraps.

`playLogo()` in app.js removes the class, forces a reflow, and re-adds it — assigning a
class twice in one frame is a no-op, which is the classic silent failure here. It then
rests 2–3 minutes (randomised, so it doesn't feel metronomic), pauses entirely while the
tab is hidden, and replays on click. `prefers-reduced-motion` leaves the cat sitting.

Tests guard it: the files ship and stay small, the sheet divides evenly into the CSS
grid *and* matches the `--fw` ratio, frame 0 is genuinely transparent, no frame runs off
its own edge, the frame count over `--play` is a sane frame rate, the rest interval is
still 2–3 minutes, and `tools/make_logo.py` exists and still explains the three traps.


## The name, and why the folders did not follow it

The product is **Mittens & Pence**. The python package is still `kestrel/`, the settings file and
the data directory are whatever they already were, and that is deliberate:

* `config.data_dir()` returns the *existing* folder when one is there — new installs get
  `Mittens & Pence` / `mithapp`, an install that already has `Kestrel` / `kestrel` keeps it.
  `db_path()` does the same for `mithapp.db` vs `kestrel.db`. Quietly moving someone's
  real accounts, credentials and history to make a rename look tidy is how you lose them.
* `MITHAPP_DATA_DIR` is the override; `KESTREL_DATA_DIR` still works.
* Renaming the python package would touch every import for no user-visible gain, so it
  did not happen. If it ever does, it is a mechanical change independent of this one.

Three tests hold this: the constants are what they claim, an existing folder wins, and a
fresh install gets the new names.

## The Help button

Bottom right, fixed, above the content. A keyed still from the same illustration set
(`help.webp`, 8 KB — the source was a cat on a black background, keyed by the same
border-connectivity method as the logo) plus the word "Help", muted at rest and stepping
forward on hover. The cat already has a question mark over its head; the word removes any
doubt.

Clicking it builds a `mailto:` and hands it to `POST /api/open-url`, which now accepts
`mailto:` alongside `http`/`https` — still a closed list, so a crafted link cannot launch
a local file, and control characters are rejected. Going through the server rather than
a bare `<a href="mailto:">` matters because the app may be running inside a native window
where a link like that does nothing; `webbrowser.open` reaches the real mail client. If
that fails the front end falls back to navigating to the mailto itself and then tells the
user the address in plain text.

The body is pre-filled with version, screen, platform and credential store — enough that
a bug report is useful without the person having to describe their setup — and
deliberately nothing about their money. The address is also on the Settings page, with a
copy button, so the button is never the only way to find it.


## PDF statements

`importers/pdfstatement.py`. A PDF has no rows and no columns — it has glyphs at
coordinates — so `extract_text()` gives a wall of words in reading order and throws away
the one thing that makes a statement a statement: that the number at x=470 is a debit and
the one at x=530 is the balance. The reader works from word positions instead:

1. **Ruled tables** are read via pdfplumber's table finder when the PDF has lines.
2. **Otherwise the grid is inferred.** Words group into lines by vertical centre; the
   header row is found by scoring against statement vocabulary (and penalising cells that
   parse as values); column spans come from the header and are then **re-fitted to where
   the data actually landed** — headers are left-aligned and money right-aligned, so the
   header's own x-range is a poor description of its column.
3. **Continuation lines are stitched.** A wrapped description has no date and no amount
   and occupies one column; it belongs to the row above.
4. A header repeated at the top of later pages is skipped by re-scoring it.
5. With no header at all, columns come from the widest data line and are named from their
   contents (dates → Date, numbers → Amount/Balance), so the existing auto-mapper still
   has something real to work with.

Output is a plain `Table`, so column mapping, remembered layouts, categorisation and the
SHA-256 fingerprint that makes re-uploading safe all work unchanged.

**`_is_money` earns its place.** `parse_amount` is deliberately forgiving and reads 4471
out of "ACCOUNT ENDING 4471" — correct when a column is known to hold money, wrong when
deciding whether a line is a transaction at all. Without the strict test, every wrapped
description became a phantom row.

**Scanned PDFs are detected and named.** No text means a picture of a statement; the
answer is a CSV from the bank or an OCR pass, and saying that is far more use than an
empty table.

**Packaging:** pdfplumber needs Pillow, which the PyInstaller spec used to exclude. That
produced a build which started perfectly and died the moment someone dropped in a PDF. A
test now asserts Pillow is not in `excludes`.


## Importing somebody else's budget spreadsheet

`importers/budgetsheet.py`, plus two routes in `web/server.py` and one screen in
`app.js`.

A household budget workbook has no agreed shape. Months tile sideways, categories run
down, subtotals sit in the middle of the data, formulas point at other sheets, and every
household invents its own layout. Absorbing one wholesale is how you end up silently
wrong, so this reads one specific thing: **the plan** — a list of categories with a
monthly amount against each.

That scopes the problem into something tractable. Spending is recomputed from statements
and must never come from here: importing a sheet's own arithmetic alongside the same
household's statements double-counts every pound, and nothing on screen looks wrong
while it happens.

**Finding the list.** A budget list is a column of text labels beside a column of
numbers. `_read_block` walks every (label column, value column) pair up to five columns
apart and keeps runs of four or more rows. Blocks are scored: +6 for a header matching
`budget|per month|p/m|planned`, +4 for a marker row nearby (`DON'T TOUCH`, `master`),
+2 when every label is distinct, +1 when a total sits under it, −4 when almost every
value is zero. Ties break towards the **later** sheet, because a workbook with a tab per
year keeps the current plan last.

**Totals are rejected twice.** By label (`Total`, `Subtotal`, `Sum`, `Net`, `Balance`)
and by arithmetic — a row whose value equals the running sum of the rows above it is an
aggregate whatever it is called. One imported total doubles the household's budget.

**Sign is normalised, not assumed.** Some sheets write budgets negative. The block
reports which, and `apply_budget` stores `abs()`: a budget is a ceiling, and a budget of
minus £150 never matches anything.

**Currency is reported, not guessed.** `_col_currency` reads the *number format* of the
value column — `[$£-en-GB]`, `[$R-en-ZA]`, `"R"#,##0.00` — and the screen says which it
found, with a selector beside it. A household with commitments in two countries writes
both in one column and only they know which is which.

**Mapping is a suggestion.** `suggest_section` prefers a category the household already
has (so importing twice doesn't create a second *Groceries*), then a keyword table, then
`Other`. It is allowed to name a section that does not exist yet: burying *Entertainment*
in *Other* because the default list happens not to include it loses the very structure
being imported. Every row's section, name, amount and tick is editable before anything
is written.

**Two things arrive unticked, with the reason shown:** a category budgeted at zero, and
anything that lands in Income or Transfers. A budget on a salary line is a category
permanently four hundred percent "over" — noise, not a number.

**A strong budget list wins over the statement reader.** No bank has ever exported a
workbook with `Budget P/M` written over a list of categories. Left to itself the
statement reader finds *a* header row in one of the working sheets and offers to import
a few hundred rows out of it. So `POST /api/import/analyse` diverts when a block scores
6 or more, and the screen carries a **"No — these are transactions"** button that
re-analyses with `?as=transactions`. `has_budget` is set on ordinary statement responses
too, so a workbook that is genuinely both offers the switch in the kind selector.

`has_budget_list()` exists separately from `find_budget_lists()` because that flag is
computed on *every* spreadsheet upload: it stops at the first strong block instead of
reading every cell of forty sheets.

**Applying is idempotent.** Missing sections and lines are created, then `set_budget`
updates in place, so running the same import twice changes the figures rather than
duplicating the categories.


## "Per year" needs a year

`engine/portfolio.py`. The old return line divided the overall return by a start date
read from `settings.portfolio_start_date`, which ships with the anchor from the original
*Investments 2* sheet (August 2021). A fresh install with three months of imported
history therefore reported a confident rate "over 5.0 yrs" — five years of data that did
not exist.

`_first_activity()` now takes the earliest date Mittens & Pence has actual evidence for — the
first trade, dividend or transaction — and falls back to the configured anchor only when
there is nothing imported at all. `annualised()` returns **None** below
`MIN_ANNUALISE_YEARS` (one year) rather than a number, and the UI says what there is
instead: *"3 months of history — too short for a yearly rate"*.

`summarise()` returns `return_on_cost` and `return_on_cost_yr` together, so the per-year
line annualises the exact ratio printed above it rather than a separately computed one
that can disagree with it.


## Editing budget sections

`engine/sections.py`. Sections were a fixed list; they are now editable from Settings.

The function that justifies the module is `rename_section`. A *section* budget stores its
section as text in `budgets.parent_only` — there is no foreign key to follow — so
renaming the section without carrying the budget across leaves a budget pointing at a
section that no longer exists, applying to nothing, with no error anywhere.

Income, Transfers and Saving are protected: renameable, never deletable. They are found
by the `is_income` / `is_transfer` / `is_saving` flags on their categories rather than by
name, so renaming *Income* to *Money in* doesn't turn somebody's salary into spending.
Deleting an ordinary section takes an optional `move_to`, so its transactions and lines
land somewhere rather than being orphaned.


## Transactions typed in by hand

`engine/manual.py`, four routes, one dialog. Everything else in the app arrives from a
file or an API with a fingerprint that makes re-importing safe. A typed row has no such
provenance, and that single difference drives the whole module.

**It can be corrected; an imported one cannot.** A mistyped amount can't be fixed by
re-importing, so `update` and `delete` work on `entry_source='manual'` rows and refuse
everything else — in words, not a 500. Letting an imported row be edited would quietly
break the guarantee that re-uploading a statement changes nothing.

**It gets out of the way when the statement arrives.** Somebody notes a £40 cash
withdrawal the day it happens; three weeks later the statement carrying that same £40 is
imported. Two rows, one payment, every budget wrong, and nothing on screen looks broken.
`find_superseded` matches on account, amount to the penny, and a date within
`MATCH_WINDOW_DAYS` (6 — a card payment takes days to post, and people write the day
they spent it), then `import_transactions` deletes the note and **says so in a warning**.
Matching is deliberately strict and one-to-one: a wrong match here deletes something
somebody typed, which is worse than a duplicate they can see and remove themselves.

**The sign is never typed.** `add()` takes `direction` ("out"/"in"), not a signed number,
and `abs()`es whatever it is given. A minus sign in a text box is the single commonest
way to enter an amount backwards, and `-40` typed into a box already labelled *money
out* would otherwise become income.

**The fingerprint carries a timestamp.** Two £3 coffees on the same day are two
transactions. An imported row is de-duplicated against the statement; a typed one is only
ever de-duplicated against itself, and somebody who types the same thing twice means it.

**A declared transfer pairs its own legs.** `categorise.detect_internal_transfers()`
guesses at imported data by matching amounts within a few days, and with several £500
movements about it can pair the wrong two. A transfer entered through this dialog is
*declared*, so `_pair()` links exactly those two rows and nothing else.

**Cross-currency transfers ask.** £500 out of a UK account is not R500 into a South
African one, and only the person's bank knows the rate it used. The far leg's amount is
required when the currencies differ, and the whole entry is validated **before the first
insert** — an earlier version wrote the departing leg and then raised, leaving money
leaving one account with nothing arriving in the other.

`entry_source` was added through `db.ADDED_COLUMNS`, defaulting to `'import'`, so
existing households keep working with no migration step.


## Mortgages

`engine/mortgage.py`, two tables, six routes, three dialogs. A mortgage added as an
ordinary account is a negative balance: net worth is right and nothing else is answered.
Everything worth knowing is derivable, and none of it falls out of a balance — the
interest/capital split, the date the fixed rate ends, what an overpayment saves, the
equity.

**No dependency.** The amortising-annuity formula is four lines, and `monthly_rate` is
deliberately `annual / 12` rather than the twelfth root of `1 + r`: lenders charge the
nominal rate divided by twelve, and using the effective rate would disagree with every
statement they send. `payment_for(250000, 4.29, 300)` returns £1,359.95, which is what
every UK calculator quotes.

**"Never" is an answer.** At 5% on £200,000 the interest alone is £833 a month, so a £700
payment clears nothing. `months_to_clear` returns **None** rather than a very large
number, `amortise` emits one row flagged `never_clears` instead of five hundred rows of a
growing debt, and the card says the payment doesn't cover the interest. Same principle as
`annualised()` and a NULL balance.

**Balances are projected and labelled.** A UK mortgage statement arrives once a year, so
a stored balance is stale for eleven months of it. `projected_balance` amortises forward
from the last confirmed figure, subtracts any recorded overpayments, and returns
`confirmed_on` and `projected_months` alongside the number so the screen can say which
part is a projection. **`portfolio.net_worth()` uses the same projection**, because a card
saying £187,989 over a net worth built from £191,988 is one app reporting two debts.

**The capital half is not spending.** `capital_repaid_between` returns the capital
repaid per category from the amortisation schedule — the statement shows one number and
never says how it divided. `budgets.spend_by_category` moves that amount from `spend` to
`saving`, reports it as `mortgage_capital`, and never moves more than actually went out
(a projection can run past a missed payment). The individual budget *line* keeps the
whole payment, because a Mortgage budget is normally set at the full amount and halving
what counts against it would read as permanently 40% used; it carries the capital as a
note instead. `unbudgeted` adds the capital back before subtracting the lines, or it
would come out short by exactly that.

**Consistency is checked, not assumed.** `term_mismatch` fires when the payment implies a
payoff more than a year after the contractual term ends — either a figure on file is
wrong or there is a real shortfall, and both are worth saying. Finishing *early* is
reported separately as `ahead_by_months`, because it is news rather than a warning. The
demo household's figures were rebuilt to pass this check: £217,000 at 4.29% over 25 years
really is £1,180 a month. Sample data that trips the app's own consistency check is a
standing bug report.

**One figure for the house.** `property_account_id` links an existing asset account
instead of retyping its value, and the form disables the free-text box when a link is
chosen — two figures for one house is how they come to disagree.

**Off-by-one, visibly.** `payoff_on` is the date of the *last payment*, not the month
after it. The schedule starts with this month's payment, so `n` payments end at month
`n − 1`; getting this wrong put "Jun 2046" on a card sitting directly above a chart ending
"May 2046", which reads as a bug even when both numbers are nearly right. A test asserts
the card, the schedule and the curve all name the same month.

**`runDownChart` rather than `lineChart`.** The generic chart is built for history: its
footer prints the change over the span, so a mortgage falling by £230,000 rendered as
"−£229,955" in red — a loss. The forward-looking chart labels both ends with month and
year, marks where the fixed rate ends, and always includes the final month so the curve
reaches zero instead of stopping at whatever the yearly sampling landed on.


## Members, and a name that should never have shipped

A member is a **label on an account** — whose ISA is whose — used to filter by person and
to scope a budget (`budgets.scope='member'`). There is no authentication anywhere in
Mittens & Pence: no sign-in, no users, no passwords. One computer, one file, one household.

`db.seed_members()` creates a single member called **"Me"**. `demo.load()` then ran:

```python
c.execute("UPDATE members SET name='Allan' WHERE is_default=1")
```

So anyone who pressed "Have a look with sample data first" had the author's name written
over theirs — and the API only ever exposed `GET` and `POST /api/members`, so there was
no way to change it back. Two defects compounding: a bad write, and no way to undo it.

Both fixed. The sample household now keeps whatever name is already there and reports it
in its own summary. `PATCH /api/members/{id}` renames, recolours and moves the
`is_default` flag (clearing it everywhere first, because "whose is this by default" needs
exactly one answer). `DELETE` takes `?move_to=`, hands the departing person's accounts and
member-scoped budgets to somebody else rather than letting the `ON DELETE SET NULL` quietly
orphan them, refuses to remove the last member, and promotes a new default if it removed
the old one. `GET` reports each member's account and budget counts, so the dialog can say
what removing them would disturb *before* the button is pressed.

A test asserts the string `Allan` appears nowhere in `demo.py` outside comments. It is the
cheapest possible guard against the same class of mistake — a developer's own details
baked into everybody's install.

**The first-run prompt.** The tour gained a step 0 with a text field, because the tour is
the one moment the app knows for certain this is a new household. `showTourStep` appends
the input when a step declares `field: 'name'`, and both Next and Skip call
`saveTourName()` — skipping the tour should not mean skipping the answer already typed.
The field never pre-fills with "Me": that is the placeholder the app ships with, not
something the person said.


## Packaging, and the same rename bug a second time

`build/mithapp.spec` had `PKG = ROOT / "mithapp"`. There is no `mithapp/` directory — the
python package is still `kestrel/`, deliberately, because renaming it would move
everybody's data folder. So `datas` pointed at two paths that did not exist, and the
build would have shipped **with no web interface and no institution registry**: an app
that starts, opens a window, and serves nothing.

This is the *second* time the blanket `kestrel`→`mithapp` rename did exactly this. The
first was `tools/build_institutions.py`, which wrote a perfect registry into a directory
nothing reads while all 82 tests passed. Neither was caught by the test suite, because
both are build-time paths that nothing imports.

Three guards now, because one clearly wasn't enough:

1. **The spec asserts for itself**, at build time, that `web/static/app.js` and
   `institutions/data/` are where it is about to look. A build cannot quietly produce an
   empty app.
2. **A test executes the spec's header** and re-checks the same paths, so `pytest` fails
   before anyone gets as far as building.
3. **A test walks `kestrel/providers/*.py`** and asserts each module is named in
   `hiddenimports`. Providers register themselves on import, so a frozen build only knows
   about the ones the spec lists; a new provider that nobody adds to the spec vanishes
   from the packaged app with no error anywhere.

**Two shapes from one spec.** `MITHAPP_ONEFILE=1` switches `EXE()` from
`exclude_binaries=True` plus a `COLLECT` (a folder) to everything packed into the
executable (one file), and skips `COLLECT` entirely. The folder starts in about a second;
the single file unpacks ~40 MB to a temp directory on each run and takes ten to twenty.
The folder is right for the developer's machine, the single file for sending — because
"download this and double-click it" survives being read over the phone, and "keep all
these files together" does not.

**`build_windows.bat` is written CRLF.** `cmd.exe` is unreliable with LF-only batch
files, particularly around the multi-line `if errorlevel ( … )` blocks the script uses to
stop on a failed test run. A test asserts every line ends `\r\n`.

**`build/Read me first.txt` ships beside the executable** and is copied there by both
build scripts. Without it the first thing a recipient meets is a full-screen
*"Windows protected your PC"*, and most people stop there. A test asserts the read-me
still names that warning, the Run-anyway route, the macOS **System Settings → Privacy &
Security → Open Anyway** route, how to tell an Apple-chip Mac from an Intel one, and the
fact that there is no sign-in.

Right-click → Open used to be the macOS route, and six places said so — including a test
asserting it. Apple has withdrawn it; on a current Mac it simply fails, and somebody sent
down that path concludes the app is broken rather than that the instructions are old.
The route in Apple's own documentation is the Privacy & Security one, and it works on
every macOS from Catalina onwards.

### The build script's own dependencies

Three faults in `build_windows.bat`, all found by running it rather than reading it:

1. **It ran pytest without installing it.** The install line was
   `pip install -r requirements.txt`; pytest is in `requirements-dev.txt`. Every clean
   machine stopped at step 3 with *"No module named pytest"* — under a message blaming
   the tests. Now it installs `requirements-dev.txt`, and checks `import pytest` first so
   a missing test runner is reported as a missing test runner.
2. **`set` resets `errorlevel`.** The one-file step cleared `MITHAPP_ONEFILE` before
   checking the result, and `set VAR=` succeeds — so a failed single-file build printed
   "Done." The check now comes first.
3. **`\"` is not an escape in batch.** A `findstr` looking for `"Google Drive"` searched
   for the literal strings `\"Google` and `Drive\"` and matched nothing.

Both scripts now call `python -m PyInstaller` rather than the bare `pyinstaller` command,
so they use the environment's own interpreter whether or not the venv's `Scripts` folder
reached `PATH`.

**`reportlab` joined `requirements-dev.txt`** for a related reason. It only *generates*
sample PDFs for the tests — the app reads them with pdfplumber and never needs it — but
without it six PDF-statement tests skipped silently, including on the machine doing the
build. "Checking everything still works" was quietly not checking the one feature that
has already caused a packaging bug. A test now asserts that anything listed in
`requirements-dev.txt` is actually importable when the suite runs, so a skip of that kind
becomes a failure instead.

### `distutils`, and why the build passed everywhere except the one machine that mattered

```
ValueError: Target module "distutils" already imported as "ExcludedModule('distutils',)".
```

`distutils` was removed from the standard library in Python 3.12 and is now supplied by
setuptools. PyInstaller's `hook-distutils` aliases the vendored copy back to the name
`distutils` — and aliasing onto a name in `excludes` is a hard error.

It needs **three** things at once:

1. Python 3.12 or newer (`compat.is_py312`),
2. setuptools present and vendoring distutils, and
3. some import chain that actually reaches `distutils` — on Windows,
   pywebview → pythonnet supplies one.

Which is why the build succeeded on Python 3.11, succeeded on Linux under 3.13, and died
on a Windows PC running 3.14. Reproduced here with a four-line script and a two-line
spec: excluding `distutils` fails, not excluding it succeeds.

`setuptools` and `pip` came out of `excludes` at the same time. They are not
dependencies, but PyInstaller's hooks alias several names *into* setuptools' vendored
tree (`backports`, `importlib_metadata`, `jaraco`), and excluding the tree those point at
invites the same failure by a different door. A few MB of build size buys the removal of
a whole class of "works here, not there".

Guarded three ways, because a packaging bug that only appears on someone else's machine
is the expensive kind: the spec asserts it for itself at build time; a test re-checks the
list; and a third test asks **PyInstaller** which names it aliases and fails if the spec's
list has drifted (skipped below 3.12, where the hook does nothing).

### `utcnow()`

`datetime.utcnow()` and `utcfromtimestamp()` are deprecated and scheduled for removal;
the 3.14 test run emitted **3,045** warnings from them. All fifteen call sites are gone.

The replacement had to stay **naive**: `dt.datetime.now(dt.timezone.utc).replace(tzinfo=None)`,
not `dt.datetime.now(dt.timezone.utc)`. Those values are stored as ISO strings and
compared as strings against expiry stamps already written to disk. A replacement that
grew a `+00:00` suffix would make every existing OAuth token compare wrong — either
permanently expired or never expiring — with nothing on screen to say why.


## A Mac is two machines, and the build machines are borrowed

PyInstaller bundles a real Python interpreter for the platform it is running on, so it
cannot cross-compile. That was always going to mean a Windows build on Windows and a Mac
build on a Mac. What was not obvious is that **a Mac build is two builds**: Apple changed
processor in 2020, an Apple Silicon build will not start at all on an Intel Mac, and an
Intel build only runs on Apple Silicon once the person has installed Rosetta. Publishing
one file and calling it "the Mac version" leaves half the recipients double-clicking
something that does nothing and produces no error to search for.

Three machines, then, and the household has one. `.github/workflows/release.yml` borrows
the other two: GitHub lends out `windows-latest`, `macos-latest` (Apple Silicon) and
`macos-15-intel`, free and unlimited on public repositories. Pushing a tag builds all
three, runs the entire test suite on each, and leaves a draft release.

Four things in that workflow are there because of a specific way it can go wrong:

* **The version is checked against `APP_VERSION` before anything is built.** Every copy
  compares the manifest's version against the number baked into the file it is running.
  Ship them different and the app either offers an update to the version it is already
  on, for ever, or is never offered one at all. Thirty seconds of checking at the front
  beats twenty minutes of building something that would have to be thrown away.
* **`lipo -archs` checks each Mac build is the processor it was asked for.** The runner
  image and `setup-python` between them decide the architecture. If either ever changes,
  the build still succeeds — and produces a file that silently will not open on the
  machines its name says it is for.
* **`ditto`, not `zip`.** A `.app` is a directory of symlinks and permission bits.
  `zip -r` flattens them; the bundle unzips looking perfectly normal and then refuses to
  launch on somebody else's Mac.
* **Every filename in `latest.json` is checked against the files actually attached**, and
  every URL against what GitHub will really serve it as (spaces become full stops). A
  manifest is a promise with a SHA-256 on it, and a name in it with no file behind it is
  a 404 for everyone who presses "Get it".

The release is left as a **draft**, deliberately. `/releases/latest/download/` ignores
drafts, so a half-right release sits there harmlessly until somebody has read it, and
every copy already out there carries on pointing at the last good one.

### The manifest learned to name a processor

`downloads` was keyed by platform alone. It now accepts `macos-arm64` and `macos-x86_64`
as well, and `updates.download_keys()` returns the specific name first with the plain one
as a fallback — so releases published before any of this existed stay installable, which
matters, because the update that delivers the new code is itself delivered by the old
manifest.

`arch_key()` deliberately returns `None` for anything not in its table rather than
guessing. A machine whose architecture we do not publish for must fall through to the
plain platform entry, not be steered towards whichever name happens to have a download
sitting behind it. And on an Apple Silicon Mac running an Intel build under Rosetta it
reports `x86_64` — the right answer, not a bug: that copy should be offered the Intel
update, because the Intel one is the one it can run.

`publish.py` warns when a platform is only half covered — `macos-arm64` present,
`macos-x86_64` missing, no plain `macos` to fall back on. That is the quiet failure in
all of this: every Intel Mac would look for a key that is not there, find nothing, and
report *"you have the newest version"* for ever, which looks exactly like nothing being
wrong.

### The version check in `publish.py` was backwards

It warned when the version being published was **not newer** than `APP_VERSION`, on the
intuition that a release should be newer than the last one. Wrong pair of numbers. The
file being hashed *is* the build, and the manifest's number is compared against that
build's own `APP_VERSION`, so the two have to be **equal**. The old check complained
about the correct case and stayed silent on the one that breaks: a manifest saying 1.2.0
over a binary built as 1.1.0 tells everybody who installs it that 1.2.0 is available —
they download it, run it, and are told again, for ever.

## Splitting a payment across categories

`engine/split.py`, three routes, one dialog. £100 at Tesco is often £50 of groceries, £20
of electronics and £30 of liquor; the bank sends one line and has no idea.

**The parent row is never altered.** It keeps the bank's amount, description and
fingerprint, so re-uploading the statement still changes nothing and the record of what
the bank actually said survives. Only `is_split` flips. The parts become child rows
(`split_of`, `entry_source='split'`) carrying the categories and the money.

That gives exactly one rule, and everything depends on it holding in every query:

> **A split parent is never counted; its children are.**

Count both and every figure in the app doubles silently — the same failure mode as
importing a spreadsheet's own totals. `db.NOT_SPLIT_PARENT` is the clause. It had to be
added in five places, found by grepping every `FROM transactions`:

| Where | Why it matters |
|---|---|
| `budgets.spend_by_category` | every budget, section total and the trend chart |
| `export/banking_xlsx` | the Transactions sheet the Budgets and Spending tabs read |
| `snapshots` | rolls a balance backwards by summing later movements |
| `categorise` | a parent isn't counted, so re-sorting it only makes screens disagree |
| `api_transactions` | the listing shows the parts, or the same money appears twice |

`detect_internal_transfers` excludes **both** sides: the parent because it is not counted,
and a part because a £50 fragment of a £100 shop matching some unrelated £50 is a false
positive that would silently remove real spending from the budget.

**The test that actually proves it** is not any of the unit tests — it is
`test_splitting_changes_no_household_total`: take the household's income, spend, saving
and net, split a real payment three ways, and assert every figure is *identical*. Then
undo it and assert the same. Nothing else catches a missed query.

**The parts must add up.** Splitting £100 into £50 + £20 + £25 loses £5: the spending
disappears, the account stops reconciling, and there is nothing on screen to notice. So
the total is enforced to the penny and the screen shows what is left rather than making
anyone do the arithmetic.

**Every part pulls the same way.** A positive part inside a payment out would *reduce*
the household's spending. And the shortfall message compares **magnitudes**, not signed
values: a payment out is negative, so `total - running` is negative when the parts fall
short — the first version read that sign directly and told people "too much" when they
had allocated too little, the exact opposite of what was wrong.

**Nobody types a minus sign.** The dialog works in positive numbers and the parts inherit
the payment's direction, as in the manual-entry dialog.

Two small ones worth keeping:

* `data-cat` was already the transactions table's categorise button. Reusing it in the
  dialog meant a document-wide `$$('[data-cat]')` bound a table handler onto a dialog
  dropdown. The dialog's attributes are `data-samt` / `data-scat` / `data-sdesc` /
  `data-srm`. Renaming them the first time also caught the blanket-rename trap again: the
  selectors changed, `el.dataset.amt` did not, and the handler crashed on every keystroke.
* Selecting a category did not call `draw()`, so the warning about parts landing in
  Income or Transfers — rendered by `draw()` — could never appear. A select is safe to
  redraw on change; a text field being typed into is not.


### The icon, and the rename's last casualty

The executable still shipped the original **Kestrel bird** — a flat two-colour mark from
before the rename. Nothing referenced it in code, so nothing caught it; the favicon had
been replaced and the app icon had not.

`tools/make_icons.py` builds the whole set from one square source: `.ico` for Windows,
`.icns` for macOS, two PNGs, and `web/static/favicon.png`. Three details it handles that
are easy to get wrong:

* **The source is cropped and de-hazed first.** The artwork carried ~12,500 pixels of
  alpha≤17 white fuzz above the card — invisible at full size, grey dirt at 16px. Rows
  and columns are kept only where more than 15% of the width is genuinely opaque, then
  anything below alpha 8 is zeroed, then it is padded to a square rather than stretched.
* **The `.ico` is assembled by hand, not by Pillow.** Pillow writes PNG entries at every
  size; that is legal, but every Microsoft tool writes BMP below 256 and PNG at 256, and
  this file cannot be tested here because the executable is built on Windows. A BMP
  inside an icon is not a `.bmp`: no file header, rows bottom-up, and the header height
  is **doubled** to cover the AND mask. Get that wrong and it opens fine in a viewer and
  shows as a blank square in the taskbar. A test checks the doubling on every entry.
* **All seven sizes are included** (16 to 256). Ship only 256 and Windows squashes it
  down itself for the taskbar, which turns to mush.

The spec now picks the icon **by platform** rather than taking the first file that
exists. That loop was harmless while only `.ico` existed; the moment `.icns` appeared it
would have handed every Mac build a `.ico`.


### Text encoding, and the second bug that only existed on Windows

```
UnicodeDecodeError: 'charmap' codec can't decode byte 0x90 in position 2197
```

`read_text()` and `open()` without an explicit `encoding=` use the **platform's**
default: UTF-8 on Linux and macOS, **cp1252 on Windows**. Every file in this repo is
UTF-8, and `index.html` carries the nav glyphs — `◎ ▲ ▤ ≡ ◑ ⇄ ⤓ ⤒ ⚙` — so a bare read
worked everywhere the code was written and failed on the one machine that builds the
executable. And because the build runs the tests first, it stopped the build.

This is the second bug of exactly that shape, after `distutils`. Both were found by
someone else running the build, which is the expensive way.

Three things now stand between it and a third:

1. **Every text read names its encoding** — eighteen in the test suite did not.
2. **A test walks `kestrel/`, `tools/` and `tests/`** and fails on any `read_text` or
   `write_text` call without one. It counts parentheses rather than reading to the first
   `)`, because `write_text(json.dumps(x), encoding="utf-8")` closes `json.dumps` first
   and a naive scan reports a false positive — which the first version of this test duly
   did, on two lines that were already correct.
3. **The build scripts run pytest with `-X warn_default_encoding`**, so the interpreter
   itself flags any read that falls back to the platform default, on the machine where
   the platform default is the problem. `pytest.ini` silences openpyxl's own temp-file
   writes: a dependency's habits should not fill somebody's build log.


## Renaming to Mittens & Pence, and the ampersand

Two rules, both learned the hard way.

**The name people read is not the name a machine gets.** `&` is a command separator in
Windows batch, so `echo Mittens & Pence` tries to run `Pence`. `config.APP_NAME` carries
the ampersand and is used only in text; `APP_FILE_NAME` ("Mittens and Pence") is what
becomes folders, executables, launcher filenames and the keyring service. The batch
scripts escape it as `^&` wherever it is echoed, and a test asserts no file in the repo
has `&` in its name.

**A blanket rename hits the values whose whole job is to hold the old name.** It did it
again here, twice, and both would have been silent:

* `LEGACY_NAMES` became `("Mittens & Pence", "Kestrel")` — so an install upgrading from
  Mithapp would not have found its own data folder and would have started empty.
* `_KEYRING_SERVICE` became `"Mittens & Pence Finance"` — and that name is the key the
  **credential vault** is stored under in Windows Credential Manager. A new service name
  cannot see the old entry, so the app would have minted a fresh key and every saved bank
  credential would have become undecryptable, with no error explaining why.

Both now have explicit legacy chains — `LEGACY_NAMES`, `LEGACY_SLUGS`, `DB_NAMES`,
`_LEGACY_KEYRING_SERVICES` — checked newest-first so a *second* rename does not send
somebody back past the install they have been using. A test asserts the current name
never appears in any legacy list, which is the general form of the mistake.

The python package is still `kestrel/`, for the same reason it survived the first rename.

## Only routes that cost nothing

Open Banking and the South African aggregators reach these banks only through a
registered provider, and none is free to a household. The routes were listed but never
recommended, which produced a screen that looked as though it could connect and then
asked for a subscription.

`next_step()` now **withholds** any `openbanking` or `aggregator` route with no free
provider, and returns it in a separate `withheld` list so the panel can still say the
bank supports it. Withholding rather than deleting matters: silently dropping the option
leaves somebody wondering why their bank appears not to support something they know it
does. Nothing free was lost — a check across all 275 institutions confirms no such route
had a free provider — and every direct API (Monzo, Starling, Trading 212, IBKR, Investec,
the exchanges) is on `direct_api` and untouched.

`repair_connections()` follows from this: an old Open Banking connection with a dead
provider now has nowhere to be re-pointed, so it is converted to statement upload and
says so. One that is genuinely working on a provider the household pays for is left
alone.

## Linking to an institution's own website

`institutions/websites.py`. Clicking the name on the setup panel opens the institution's
site, through `/api/open-url` so a native window opens the real browser rather than
navigating the app away from itself.

**Every URL was verified by fetching it and confirming the site says whose it is.** That
is not fussiness: sending somebody to a *nearly* right banking domain is how people get
phished, and a finance app that links to the wrong bank has done real harm. 33 of 275
institutions have a link; the rest have none, and their written "where to find your
statements" instructions still do the job. Adding to the list means fetching the site,
not recalling a plausible domain.

## Pasting

Two different problems arrive as "I couldn't paste it in".

`Ctrl+V` doing nothing in a text box is a *host* problem: in a browser the OS handles it,
but inside a native window it depends on the host forwarding the accelerator, and
pywebview does not always. Rather than guessing, the page watches: a Ctrl/Cmd+V keydown
that is **not** followed by a real `paste` event means the host swallowed it, so the
clipboard is read directly and inserted. Where paste already works, nothing intervenes.

The second is wanting to paste *rows* rather than upload a file. The Import screen takes
a pasted block of tab- or comma-separated text and pushes it through the same reader a
dropped file uses, so mapping, de-duplication and the preview all behave identically.
That listener is removed in `render()` via `S.cleanup`, or every visit to the screen
leaves another one behind and one paste fires the handler five times.

## Updates, and the line they deliberately don't cross

`kestrel/updates.py`, `docs/PUBLISHING.md`, `tools/publish.py`.

A copy fetches a small JSON manifest from a fixed https address about once a day,
compares its `version` against `config.APP_VERSION`, downloads the build for this
platform, and verifies it against the SHA-256 in the manifest. Then it stops.

**It never replaces the running program.** The executable is not code-signed. An
unsigned program that reaches out to the internet, downloads another program and
overwrites itself is doing precisely what every antivirus is built to catch, and if a
download ever went wrong the household would be left with a broken file where their
working app used to be. So the flow ends at "here is a verified file, close the app and
run it" — and `test_a_download_never_replaces_anything` greps the module for
`sys.executable`, `os.execv`, `subprocess` and `shutil.move` to keep it that way.

What the manifest is trusted for, and what it isn't:

* **Trusted**: which version is current, and what the correct checksum is. It is the
  trust root; if it is tampered with, nothing downstream saves anybody.
* **Not trusted**: where the file lands. `filename` is reduced to a bare basename, so
  `../../../autostart/x.exe` becomes `x.exe` in the updates folder.
* **Not trusted**: what a "download" may be. https only; a 64-hex `sha256` or no
  download is offered at all; and the host must be the manifest's own or on
  `ALLOWED_DOWNLOAD_HOSTS`. That list is a typo catcher rather than a security boundary
  — suffix-matched, so `github.com.evil.net` does not pass for containing the name.
* **Not trusted**: version strings. Anything `parse_version` can't read compares as
  "not newer", so a malformed manifest can never push somebody to a download.

A file that fails its checksum is **deleted**, not left on disk looking like an update
somebody could double-click. `1.0.10 > 1.0.9` because the comparison is numeric per
component; a pre-release sorts below its own release.

### `error` is a reserved word in this app's API

`state()` reports its explanation as `last_error`, not `error`. Every API reply goes
through one front-end helper that reads a top-level `error` as "this request failed" and
throws — so a status payload whose whole job was to carry an explanation got swallowed
as a broken request, and the screen said it couldn't read the update status instead of
saying *why the check failed*. Exactly the situation where the explanation matters most.

## The local server is not as local as it looks

Binding to `127.0.0.1` stops other machines. It does not stop other *pages*: every site
the household opens is also running on this computer, and a page can POST to
`127.0.0.1:8765` in the background. Before this, any website could have wiped the
database through `/api/demo/clear`, and a site pointing its own domain at 127.0.0.1
(DNS rebinding) could have read every transaction in the house.

Two checks in `_dispatch`, so no route can opt out:

* **`Host`** must name the loopback address. A rebound domain arrives carrying its own
  hostname and is refused.
* **`Origin`** must be ours on anything that changes state, and `Sec-Fetch-Site` must
  not say `cross-site`. `Origin: null` — what a sandboxed iframe sends — is refused;
  reading it as "no origin, must be a local tool" would hand any page a way straight in.

A *missing* Origin is allowed, because curl, the tests and the desktop shell send none
and a browser cannot omit it on a cross-site POST.

## A copy for your phone

`kestrel/export/phone.py`. One HTML file, everything inlined, no network of any kind —
`test_it_is_genuinely_self_contained` fails the build on a single `http`, `<img>`,
`<link>`, `@import` or `fetch(`, because "open it on a phone with no signal" fails
silently and only for the person standing in a car park.

Two things worth knowing:

* **Dates are built by hand.** strftime's no-padding flag is `%-d` on Unix and `%#d` on
  Windows, and this app is mostly run on Windows. There is no `strftime(` in the module
  and a test enforces it.
* **It says when it was made, in words, at the top.** A stale balance that looks current
  is worse than no balance at all.

The alternative — a real iPhone/Android app — means writing the whole thing again in
another language, paying two app stores, and keeping three versions in step, for a
screen you glance at. A PWA would need the server running, which is the one thing a
phone doesn't have.

## Where the money sits, and a ring that disagreed with the headline

The Dashboard donut took `Math.abs()` of every net-worth group, which put a £188k
mortgage in as though it were an asset and produced a figure in the middle — labelled
"total" — of roughly twice the net worth printed a few centimetres above it. Two
contradictory totals on one screen.

The ring is now what you **own**; what you **owe** is a line underneath, and the net
worth below that reconciles exactly with the headline. `Math.abs(value)` in that block
is guarded by a test.

## The brand block, and one number it is all derived from

An earlier attempt at making the brand prominent had the card break out of the rail and
sit over the main column, with matching left padding on the topbar so headings cleared
it. Allan didn't like it, and he was right: a panel that overlaps the thing next to it
has to be compensated for everywhere else, forever.

It is stacked inside the rail instead — logo, then name, then subtitle — which is what
buys the prominence. Side by side, a fifteen-character name next to a logo worth looking
at leaves no width for either in a sidebar; that is what pushed the first version out
over the main window in the first place.

**Everything is `calc()`ed from `--rail`**, which is itself `clamp(216px, 16.5vw, 280px)`:

| | |
|---|---|
| `.app` columns | `var(--rail) 1fr` |
| logo `--f` | `min(calc(var(--rail) * .40), 12.5vh)` — also capped against window *height*, so a short laptop window doesn't get a cat taking up a third of the sidebar |
| `.brand-name` | `calc(var(--rail) * .088)` |
| `.brand-sub` | `calc(var(--rail) * .047)` |

So the brand holds the same proportion against the main area at every size — 216px rail
and an 86px logo at 1280 wide, 280 and 112 at 1920 — instead of a fixed 62px cat that
looks lost on a big monitor and crowds a small one. Measured at seven window sizes: the
name stays on one line and inside the rail at all of them.

The narrow-window rule redefines `--rail: 68px` rather than the grid column, so the logo
comes down in proportion with everything else.

### The collapse rule was hiding the wrong element

`#nav button span:last-child { display: none; }` matched the **icon**, because the label
was a bare text node with only the icon in a span. A window under 900px therefore hid the
icons, kept the labels, and let the labels spill out of a 68px rail. Labels now live in
`.lbl` and a test asserts there is one per nav button.

## Shopping against Food & Drink, and the shop that sells everything

*Consumed* against *bought and kept*, decided by the **shop** rather than the basket —
because the bank sends one amount for one Tesco trip and has no idea what was in the
trolley. Splitting a payment is how you say otherwise, and the parent row stays exactly
as the statement sent it.

Shopping's children were all specific — Clothing, Electronics, Hobbies, Books, Gifts —
so a general shop had nowhere to land. **Amazon was filed under Electronics for want of
anywhere better**, which made a nappy order and a kettle both read as gadgets, and John
Lewis, Wilko, Poundland and B&M fell through to Uncategorised entirely. There is now a
`Household & general` child, and the marketplaces point at it.

Three false positives found by running the categoriser over realistic descriptions
rather than reading it:

* **`\bnext\b`** claimed *"NEXT DAY DELIVERY CHARGE"* as clothing. One of the commonest
  words in English, matched bare. Now needs `retail|plc|stores` after it.
* **`\bgift\b`** claimed *"GIFT AID DONATION"* as a present. Gift Aid is a charitable
  donation and now routes to Giving › Charity.
* **`\bgas\b(?!.*station)`** filed *"PETROL STATION GAS"* as a utility bill. The
  lookahead only looked **forward**, and the word "station" was behind it. Anchored to
  the start of the line so the exclusion sees the whole description.

## Both seeders stop dead, and anything added later never arrives

`seed_categories()` returns early once a database has any category; `seed_builtin_rules()`
once it has any built-in rule. **Both are right to** — re-running either would resurrect
a section the household deleted and undo a rename.

The consequence is a quiet one: a category or a corrected rule added after the first
release reaches **new installs only**, and every copy already out there keeps the old
behaviour forever. Nothing errors. The fix is the same shape as `ADDED_COLUMNS` —
recorded, one-off steps, keyed in the `meta` table under `did:`:

* `db.ADDED_CATEGORIES` + `_apply_added_categories()`
* `categorise.RULE_UPDATES` + `apply_rule_updates()`

Three properties, each with a test:

1. **Idempotent.** Applying twice changes nothing.
2. **A deletion stays deleted.** The marker is written even when the step does nothing,
   so a section the household removed is not recreated on the next launch.
3. **An edited rule is theirs.** A correction is applied only if the pattern is still
   *exactly* as it shipped. Quietly rewriting somebody's own rule would be worse than
   leaving the original bug in place.

## "Needs a look" had nothing behind it

The dashboard card built its rows from `sync.health()`, which has always attached a
`connection_id` or `account_id` to each item — and the front end rendered the text and
**threw the ids away**. So the first screen told you something was wrong and then made
you go and find it.

Each issue now carries `action` (where to go, what to open) and `do` (what the link
says), and each row is a button. An item nobody can act on has no business being on the
front screen.

## The statements folder

`kestrel/inbox.py`. A folder the app makes for itself in the user's Documents — not in
its own data directory, which lives somewhere like `AppData\Local` and is exactly where
nobody will think to drop a file. Sync everything empties it.

**The same two gates as the Import screen, and for the same reason.** A file goes in
unattended only when the layout is one the app has been taught **and** the filename
names an account distinctively. Either alone is not enough: four banks can share a
column layout, and a remembered layout says nothing about *whose* account a file is.
Anything failing a gate stays exactly where it is and is reported — the sync dialog
lists them, the Import screen lists them. Nothing is guessed, and nothing is deleted,
ever.

**Content hash, not filename**, decides what is new: renaming a file is not a reason to
import it again. Belt and braces on top of the per-row fingerprints, which already make
a double import harmless.

**Receipts are kept, not read.** Images are filed by month and left alone. Extracting
figures from a photograph would put invented numbers into somebody's budget, and the
UI says so in as many words rather than implying more.

`suggest()` returns a whole report — kind, columns, confidence, a sample — and the
field-to-column map is one key *inside* it. Iterating the report itself put a list of
column names where a column index belonged, and the import died on
`'<' not supported between instances of 'list' and 'int'`.

## The monthly reminder, and why it is not an email

Asked for as "an automatic monthly email". **A program on somebody's own computer
cannot send one**, and it is worth writing down why, because the question will come
back:

* **A mail server of ours.** There isn't one. It would mean collecting every family
  member's address somewhere central, and an API key baked into a distributed .exe is a
  key anybody can extract — which is how a sending account gets terminated for spam.
* **Their own mail account.** Supported, off by default. It means typing an email
  password into an app, which is the exact habit nobody should be taught; the
  credentials go in the encrypted vault, never in `settings.json`.
* **A `mailto:` link.** Opens a compose window, and needs the app open with a person
  sitting at it — precisely what a reminder exists to replace.

So `kestrel/reminders.py` delivers it two ways that work: **a calendar entry** (one
`.ics`, added once, repeated monthly by the household's own calendar, which alerts them
on their phone and will email them if that is how they have it set up), and **a strip
across the top of the app** on and after the day until something has actually been
imported that month.

**The day.** 1–31, and 29, 30 and 31 all mean *the last day* — 28 in February, 29 in a
leap year, and 28 again in 2100, which is not one. `calendar.monthrange` knows the
century and 400-year rules; hand-rolled leap-year arithmetic is a classic place to be
subtly wrong for seventy-four years. In the `.ics` that is `BYMONTHDAY=-1`; a literal
`BYMONTHDAY=31` would **skip every month without a 31st**, which is the opposite of
what was asked for. The file is checked by a real iCalendar parser in the tests.

### HTTP headers are latin-1

The `.ics` download set `Content-Disposition` with the app's real filename, which has an
em dash in it. Browsers rejected the whole response as "header without colon" — a broken
download with nothing in the log. Now: a stripped ASCII filename for every client plus
RFC 5987 `filename*` for the real one, and `_send` coerces every header value to latin-1
so this cannot happen again from somewhere else.

## The pre-release sweep

The last pass before publishing, written down because most of what it found was the same
shape: a screen that stated something with more confidence than the data behind it
deserved, or a control that could not be undone.

### Hide amounts had to actually hide them

It toggled a `blur` class onto `.money` and `.big`, and **neither class exists anywhere
in this app**. The only thing that ever blurred was the four headline tiles; every table
amount, every balance and every recent transaction stayed in plain sight behind a button
labelled "Hide amounts". Three changes:

* The classes it toggles are `.v`, `.num` and `.pv`, all of which exist, and a test
  cross-checks each one against `styles.css` so a fourth ghost class cannot be added.
* `.pv` is new: it marks a figure written into a sentence, where there is no table cell
  to carry `.num` — "+£13,852 on £31,834 in", the mortgage-capital note, the total in
  the middle of the donut.
* **An SVG `<title>` is drawn by the browser itself and no CSS can blur it.** Hovering a
  chart point read the balance out loud with hiding on. Chart tooltips now go through
  `tip(before, amount, after)`, which writes the visible text and stashes a `•••`
  version in `data-h`; `applyPrivacy` swaps the two. A test forbids a literal `<title>`
  anywhere in `app.js`.

Calling `applyPrivacy()` at the end of every render was the old plan, and it leaked every
time somebody added a dialog. A `MutationObserver` on `document.body` re-applies it for
anything that appears afterwards, whoever wrote it. It only does work while hiding is on,
and it writes `textContent` only when the text differs — assigning the same string still
replaces the text node, which the observer would see as a change, for ever.

### Numbers that did not follow from the numbers beside them

* **The month card.** It showed In, Out and Left over, where left over is income less
  spending *less what was put by* — and "put by" was not on the card. £0 in, £2,290 out,
  −£3,985 left over, and nothing to account for the missing £1,695. Put by is the fourth
  tile now, and a test asserts `net == income − all_spend − saving` against the engine.
* **Rounded and unrounded on one screen.** The four Budget tiles passed `{round: true}`
  and the table under them did not, so a £42.50 budget appeared as £43 directly above
  itself. The tiles no longer round: `money()` already drops the pennies above £1,000 on
  its own, which is the rule the whole app follows everywhere else.
* **`{ dp: 0 }` in prose.** Left as it was — a sentence is not a column.

### Unknown is not zero, again

The same rule from further up this document, applied to three more screens: "Across every
account" summed `balance_base || 0`, so a list where nothing had been imported added up
to a confident **£0** and a list where half the balances were missing added up to a
figure that was simply wrong; a fresh copy reported "£0 · 1 group" because `net_worth()`
inserted an `Investments` key whether or not there was anything in it; and the Investments
tiles opened on "RETURN 0.0%" and "0.0% of what you put in", which reads as a portfolio
that has gone nowhere rather than one that does not exist. All three now say "—" and name
what is missing.

### Things that could not be undone

* **"Record a sale"** saved a row with no symbol and no figures if you pressed Save on
  the empty form, and there was no DELETE route, so the only way to remove it was to
  clear the database. Validated on both sides now, and every row has a remove button. A
  sale found in an imported activity file says so when deleted — it will come back the
  next time that file goes in.
* **Loading the sample data twice** built a second household. The transactions inside it
  deduplicated properly, which is why the tests never caught it; the accounts around them
  did not, so you got two Freetrade ISAs, two houses, two mortgages and exactly twice the
  net worth. Every part of the sample data is keyed on a fixed `demo:` id and reused, so
  `demo.load()` is idempotent.
* **"Clear everything"** sat under the *Sample data* heading, which reads as "clear the
  sample data" — and it deletes every real account and every real transaction too. It has
  its own card and its own heading now, and says in the confirmation what it takes with
  it and what it leaves (exported workbooks are files of their own).

### Screens that went stale in front of you

"Already built" and the statements-folder counters were rendered once at page load and
never again, so pressing Build put a green box on the screen and left "Nothing built yet"
underneath it. Both redraw from a fresh fetch after the action. The export listing also
globbed `*.xlsx` only, so the phone copy — an `.html` file — was never in it at all,
whatever the list was redrawn from.

### A failed update check is not an unpublished app

`_read_manifest` treated 403 the same as 404 and said "Nothing has been published at that
address yet" — which is a statement about the publisher when a blocked office network or
a captive portal is the actual cause. Only 404 means that now; 401/403/407 say the server
refused the request and some networks block it. The state also carries `attempted_at`
alongside `checked_at`: one is the last time an answer came back, the other the last time
we tried, and conflating them put "Last looked: never" under a message about a check that
had just failed. `RETRY_INTERVAL` (30 minutes) applies after a failure instead of the
20-hour `CHECK_INTERVAL`, because a laptop that was offline for five minutes should not
wait a day.

### Sample data has to be a plausible statement

The generated card payments were always kept to dates that had already happened. The four
rows that arrive on the same day each month were not, so a copy opened before the 26th
showed **next week's salary as money already received** — a statement no bank would hand
you, and a month's income overstated on the Dashboard. The Capitec file also wrote its
running `Balance` column in the order the entries happened to be listed rather than in
date order, which matters because that file is the fixture the CSV importer is tested
against: it is built oldest-first and reversed, not re-sorted, because sorting by date
shuffles same-day rows out of the order their balances were worked out in.

### A catalogue is a hint, not a wall

The "Account type" dropdown was exactly the institution's `account_types` and nothing
else, so somebody adding a **Nationwide** current account — one of the commonest in the
country — could choose Savings, Cash ISA or Mortgage and nothing else. The institution's
own products still come first; everything else follows under "Anything else". Nationwide
and Cumberland were also the two building societies in the list that really do offer
current accounts, checked against their own websites rather than assumed.

### Two categorisations that were confidently wrong

* **Dual-fuel energy.** Almost every British supplier sells gas and electricity on one
  direct debit, and "BRITISH GAS DD 11223" says who sent it, not which fuel it is for.
  All of them were filed under *Electricity* — a coin toss dressed as a category. There
  is now `Utilities › Energy` for the ones nobody can tell apart; *Electricity* and *Gas*
  are kept for the bills that really are one thing (Eskom, City Power, a prepaid meter, a
  Calor delivery). Energy is listed **before** Gas in `BUILTIN` so it claims "BRITISH GAS"
  before the bare `\bgas\b` pattern can.
* **Supermarket forecourts.** "TESCO PETROL 4021" went into the weekly groceries, moving
  a tank of fuel into the food budget every time anyone filled up. A forecourt pattern
  sits above the grocers now.

Both reach existing installs through the one-off migrations (`ADDED_CATEGORIES`,
`RULE_UPDATES`) rather than only fresh ones — a fix that lands on new installs only fixes
nobody's data.

### The tour

* Steps 1 and 2 both spotlighted `.brand`, so the highlight sat on the same corner twice
  running, which reads as a tour that has got stuck. Name and email are one card now,
  which is also one moment: "who are you".
* `showTourStep` assigned `tourAt = i` **before** testing `i > tourAt` to work out which
  way the person was going, so the test compared `i` with itself, always came out false,
  and a step with a missing element walked the tour backwards however you had arrived —
  down to step 0, and, if step 0 was the missing one, calling itself with 0 for ever.
* A typed-wrong email address wrote a note under the box and then advanced anyway, tearing
  the note down in the same frame. `saveTourAnswers()` returns false and the step stays.
* The card is positioned next to its target and **then grows**: the statements-folder step
  fills its path in from the server afterwards. On a 900×600 window the Next button ended
  up below the fold. A `ResizeObserver` re-places it, and the card scrolls as a backstop.

### The Help button had nothing underneath it, and everything underneath it

It was `position: fixed` in the bottom-right corner. Fixed means it floats over whatever
is in that corner of the *viewport*, so scrolled halfway down the Dashboard it sat
squarely on "Less what you owe −£187,989". `.view`'s 60px bottom padding cleared it at the
very end of the page and nowhere else. It lives at the foot of the rail now, above Sync
everything, where there is nothing to cover.

`.stat` also gained `align-content: start`: as a grid item it was stretching its rows to
the tallest tile in the row, so a tile with no sub-line sank its figure to the bottom
while the ones beside it kept theirs at the top.
